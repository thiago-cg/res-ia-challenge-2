O caminho de uma pergunta até a lei.

O ZELIA recebe uma dúvida sobre violência doméstica, decide se há risco imediato, recupera dispositivos legais oficiais e responde com citação verificada sempre que há base legal. Quando não há, ele diz isso.

01 Entrega

O que está pronto, o que foi medido e o que falta.

Esta página documenta um protótipo técnico, não um produto publicado. A tabela separa o que rodou de verdade do que ainda depende de revisão humana.

O sistema responde perguntas jurídicas de mulheres em situação de violência doméstica com base em dispositivos oficiais. Ele não dá veredito sobre o caso, não promete resultado e não substitui a Defensoria Pública. A resposta mostra a fonte; quando não há evidência suficiente, o sistema se abstém.

A stack do protótipo é Python 3.12 com FastAPI, Postgres com pgvector, Qdrant 1.15.3, Qwen3 Embedding 8B via OpenRouter e deepseek/deepseek-v4.1-flash-1017 como gerador, com o provedor fixado em deepinfra/fp8. O app padrão usa LLM_PROVIDER=mock; os números desta página vêm das rodadas com o provedor real.

O que o ZELIA é

  • Um assistente que explica direitos, prazos e caminhos com base em textos legais oficiais.
  • Um sistema que cita o dispositivo recuperado e mostra a fonte em vez de escrever a citação de memória.
  • Um sistema que desvia risco imediato para 190 e 180 antes de qualquer busca.
  • Um protótipo auditável: a mesma pergunta produz a mesma recuperação, sem reescrita por LLM no caminho padrão.

O que ele não é

  • Não é advogada, Defensoria, juíza ou órgão de segurança pública.
  • Não dá veredito, não promete resultado e não substitui atendimento presencial.
  • Não usa Jusbrasil nem doutrina raspada. Doutrina está fora do MVP por restrição de licença.
  • Não está pronto para publicação: faltam revisão jurídica humana, aprovação nos limiares de avaliação e latência interativa.

Onde não houve medição, está escrito.

Os números desta página vêm dos relatórios de 7 e 9 de novembro de 2026. Eles comparam estratégias no mesmo corpus e no mesmo conjunto de perguntas. Não são uma medida de cobertura da lei e não substituem avaliação humana.

02 Princípio

A resposta obedece a quatro regras antes de obedecer ao modelo.

O LLM é a última peça, não a primeira. Risco, versão, formato da citação e abstenção são decididos por código determinístico.

  1. 01

    Risco imediato não passa pelo RAG.

    Um classificador roda antes de qualquer busca. Se a mensagem descreve perigo agora, a resposta é o bloco fixo com 190, 180, 100 e 197. O banco, o índice e o modelo não são chamados.

  2. 02

    Sem ID recuperado, não há afirmação jurídica.

    O modelo escolhe device_ids do contexto. Ele não escreve o número do artigo nem monta a citação. Quem formata "Lei nº 11.340/2006, art. 7º, caput, inciso III" é o sistema, a partir dos metadados do banco.

  3. 03

    A lei tem data.

    Cada dispositivo é identificado pelo par (device_id, norm_version_id). Quando a pergunta traz a data do fato, a recuperação filtra a versão vigente naquela data. O modelo nunca escolhe a versão.

  4. 04

    Na dúvida, abstenção.

    O verificador confere se a citação existe no contexto, se a versão confere, se o texto citado é o literal do banco e se toda afirmação tem lastro. Se algo falha depois das duas tentativas, a resposta segura substitui a resposta.

Decidido por código

  • Se a mensagem é emergência.
  • Quais dispositivos entram no contexto.
  • Qual versão da lei vale para a data do fato.
  • Como a citação é escrita.
  • Se a resposta é aceita ou se vira abstenção.

Decidido pelo modelo

  • Como explicar o dispositivo em linguagem simples.
  • Quais dispositivos do contexto sustentam cada afirmação.
  • Quais próximos passos e encaminhamentos apresentar.
  • Se o contexto é insuficiente para responder.

Tudo que adicionou julgamento de LLM no laço perdeu. Tudo que adicionou estrutura determinística da lei ganhou.

Síntese do benchmark de recuperação, novembro de 2026

O texto recuperado é dado, nunca instrução.

Os dispositivos entram no prompt dentro de <documento>, depois de sanitização. O prompt de sistema manda ignorar qualquer ordem que apareça dentro do texto legal. A saída do modelo ainda passa por um parser que só aceita IDs presentes no contexto.

03 Fluxo

Oito etapas entre a pergunta e a resposta.

Cada etapa tem uma entrada, uma decisão e uma saída. O painel mostra o que o sistema faz e, principalmente, o que ele se recusa a fazer.

Recuperação aumentada por geração, aqui, significa uma coisa específica: buscar o texto legal antes de responder e limitar o modelo a esse texto. A resposta não vem da memória do modelo. O fluxo abaixo é o caminho completo, incluindo as saídas que não produzem uma resposta.

Etapa 01

Pergunta

A mensagem chega em linguagem comum. O sistema extrai a data do fato quando ela aparece e não pede dados pessoais.

Entra
Mensagem da pessoa; data do fato opcional.
Faz
Extrai expressões como “há dois anos” ou “em 2023” e mantém a pergunta original como consulta.
Sai
Texto da pergunta e fatos da consulta.
O que não acontece
Pedir nome, CPF, endereço ou documento. A interface avisa sobre PII antes do envio.

Etapa 02

saída não linear

Portão de risco

Antes de qualquer busca, um classificador determinístico decide se a pessoa está em perigo agora.

Entra
Mensagem normalizada, sem acentos.
Faz
Três camadas: formas iminentes; habituais com marcador de presente; passadas, exceto pergunta sobre prazo ou “só agora”.
Sai
Bloco fixo com 190, 180, 100 e 197; ou segue para a próxima etapa.
O que não acontece
Deixar a emergência para o LLM. Tocar no banco, no índice ou no modelo antes do risco.

20/20 emergências roteadas; 0 falso-positivo em 130 perguntas não-emergência.

Trecho
if classify_risk(message).immediate:
    return emergency_answer()

Etapa 03

saída não linear

Citação explícita

Se a pergunta já nomeia um artigo, o sistema tenta resolver a citação diretamente, sem busca híbrida.

Entra
Menção como “art. 7º”, “24-A, III” ou “artigo 22, inciso III, alínea b”.
Faz
Interpreta norma, artigo, parágrafo, inciso e alínea; consulta o catálogo; escolhe a versão pela data do fato.
Sai
Dispositivo explícito hidratado; ou abstenção “citação explícita não encontrada”.
O que não acontece
Cair em silêncio para a busca híbrida quando a citação pedida não existe.
Trecho
resolve_explicit_citation(message, catalog=..., data_fato=...)

Etapa 04

Entendimento e expansão

A consulta ganha vocabulário jurídico por regras determinísticas. A pergunta original não é substituída.

Entra
Pergunta e fatos da consulta.
Faz
Mapeia linguagem coloquial para termos legais: “ameaça” vira art. 147, prazo de 12 meses e violência doméstica. Mantém a consulta original.
Sai
Consulta expandida; no padrão, uma subpergunta.
O que não acontece
Reescrever a pergunta com LLM por padrão. A reescrita perdeu 22 pontos de recall.
Trecho
expand_legal_query(text)  # acrescenta termos curados

Etapa 05

Busca híbrida

Duas buscas independentes rodam no mesmo recorte de vigência e são fundidas por posição.

Entra
Consulta expandida e data do fato.
Faz
Postgres FTS sobre search_text sem acentos; Qdrant denso 4096d; RRF k=60 com peso lexical 0,2; filtro de versão.
Sai
Candidatos fundidos, até 50 por perna.
O que não acontece
Confiar num único índice. Peso lexical 1,0 derruba o recall para 0,576.
Trecho
hybrid_search(plan, dense=..., fts=..., lexical_weight=0.2)

Etapa 06

Seleção e contexto

O sistema remove o excesso do mesmo artigo, preserva a ordem e hidrata cada dispositivo na versão certa.

Entra
Candidatos fundidos.
Faz
Teto de 3 por artigo com ordem global preservada; expansão para o artigo quando ele existe; hidratação por (device_id, norm_version_id); orçamento de 6.000 tokens.
Sai
Até 10 dispositivos com texto literal, citação e metadados.
O que não acontece
Promover a linha do artigo para o topo do grupo. A mudança custou 11 pontos e foi removida.
Trecho
dedupe_by_artigo(ranked, max_per_article=3)[:10]

Etapa 07

Geração

O modelo recebe o contexto delimitado e devolve um JSON com IDs, não com citações escritas à mão.

Entra
Prompt v2 e até 10 dispositivos.
Faz
Explica, escolhe IDs e propõe próximos passos. O parser valida o schema e rejeita ID fora do contexto; até duas tentativas com feedback.
Sai
Resposta e citacoes[{device_id, afirmacao}].
O que não acontece
Aceitar artigo inventado, markdown fora do JSON ou conhecimento fora do contexto.

Regra do prompt: use apenas os dispositivos fornecidos no contexto.

Etapa 08

saída não linear

Verificação e saída

O verificador confere cada citação contra o banco. Só então a resposta é renderizada com fontes.

Entra
Resposta e dispositivos recuperados.
Faz
Confere par e versão, metadados, texto literal, aspas e lastro de cada afirmação. Aceita, regenera uma vez ou abstém.
Sai
Resposta com citação canônica e fontes; ou abstenção segura com motivo.
O que não acontece
Publicar citação sem lastro. Ocultar a falha atrás de uma resposta plausível.
Trecho
verify(answer, retrieved, repo=repo)  # accept | regenerate | abstain

Saída de emergência

Se a etapa 2 dispara, o fluxo termina aqui.

O bloco fixo é devolvido antes de qualquer busca, sem tocar no banco, no índice ou no modelo.

04 Dados

A lei vira uma árvore, e cada folha tem uma data.

A unidade indexada é o dispositivo: artigo, parágrafo, inciso, alínea. Normas e versões ficam no Postgres; o Qdrant guarda os vetores.

Um bloco fixo de 500 tokens corta o artigo no meio e mistura incisos de normas diferentes. O dispositivo é a menor unidade que pode ser citada, hidratada e verificada. Por isso o índice não guarda "pedaços de texto": guarda folhas da árvore legal, cada uma com um identificador e uma janela de vigência.

05 Recuperação

A busca que ganhou foi a mais simples que continuou auditável.

Duas pernas, uma fusão e três decisões medidas. O que parecia sofisticado perdeu para regras determinísticas e um dedupe corrigido.

A configuração atual é híbrida. A perna lexical usa o Postgres FTS com to_tsvector('portuguese', search_text), websearch_to_tsquery e escore IDF. A perna densa usa o Qdrant com Qwen3 Embedding 8B em 4096 dimensões. As duas listas se fundem por RRF, que combina as posições e não os escores, com k=60 e peso lexical 0,2. A expansão de consulta é determinística, feita por regras, e o teto é de 3 dispositivos por artigo, preservando a ordem global. O Postgres é a fonte da verdade e o Qdrant é o índice; a hidratação é por (device_id, norm_version_id), o que amarra cada resultado à versão da lei.

Essa não é a configuração mais precisa no papel. O denso sem teto marca 0,776, o híbrido sem teto 0,771 e o híbrido com teto 3 fica em 0,762. A escolha não vem do topo da tabela. É a configuração que combina precisão suficiente com degradação graciosa e auditabilidade: se o provedor de embedding falha, a perna lexical sustenta a resposta; o teto de 3 mostra artigos diferentes; e o caminho sem LLM na consulta pode ser repetido e auditado.

O que a tabela mede

A tabela compara seis configurações nas mesmas 110 perguntas respondíveis. O corpus, o índice e a passada de embedding são os mesmos; só a estratégia muda. O recall@10 mede a fração dos dispositivos-ouro que entram no top-10. O artigo@10 aplica a mesma conta no nível do artigo. O denso medido é o Qwen3 Embedding 8B no Qdrant; o Harrier local não entrou nesta rodada. As outras 40 perguntas do conjunto são de emergência ou fora do corpus e ficam fora do recall.

A diferença de 1,4 ponto entre o denso sem teto e o híbrido com teto 3 é ruído. Com 110 perguntas, o erro-padrão de uma proporção em torno de 0,77 fica entre 3 e 4 pontos pela aproximação binomial; o valor real é menor, porque o recall é uma média de frações por pergunta. As decisões que importam estão a 3 ou 5 erros-padrão de distância. O dedupe vale +11,4 pontos, a expansão +13, o doc2query −21, a reescrita por LLM −22 e o reranker LLM −20. Por isso o desempate entre as três primeiras configurações não é acurácia.

A ordem do dedupe valia 11 pontos

A função dedupe_by_artigo agrupava os candidatos por artigo e promovia a linha do artigo ao topo do grupo. A folha quase sempre pontua acima do próprio artigo, e o ouro é de dispositivo. A promoção empurrava dispositivos corretos para fora do top-10. O defeito de ordenação custava 11,4 pontos. Mantendo o mesmo teto de 3 e mudando só a ordem, o recall@10 subiu de 0,648 para 0,762, e o artigo@10, de 0,776 para 0,835. A função agora apenas remove os excedentes do grupo. O ganho veio sem tocar em modelo, índice ou embedding.

O que foi tentado e rejeitado

As seis estratégias abaixo foram medidas no mesmo corpus e nas mesmas 110 perguntas. Todas perderam para as regras determinísticas.

O padrão se repete em todas as linhas. A transformação por LLM substitui a pergunta da vítima por vocabulário jurídico genérico e apaga o detalhe que discriminava o artigo. As regras curadas acrescentam termos jurídicos sem descartar a fala original. Nenhuma das seis estratégias pagou o custo extra.

Por que a perna lexical fica

Sozinha, a perna lexical entrega 0,414. É pouco, mas é o piso do sistema. Se o provedor de embedding cair, a busca textual continua respondendo com o que o Postgres tem indexado; o denso puro devolve zero. O documento de estratégia registra uma queda real do provedor nesta rodada.

A permanência da perna lexical acompanha duas outras escolhas. O teto de 3 por artigo evita que os dez slots sejam preenchidos por parágrafos do mesmo artigo e mostra dispositivos de normas diferentes. A ausência de LLM na consulta mantém o caminho determinístico: a mesma pergunta produz a mesma recuperação. A perna lexical não é fonte de acurácia quando o denso está saudável. É garantia de continuidade, diversidade e auditoria.

O contrato de citação decide o reranker.

O reranker LLM marca artigo@10 0,873 e MRR 0,519, os melhores do lote, mas derruba o recall por dispositivo para 0,561. Ele escolhe o artigo certo e cita a linha do artigo em vez do parágrafo que o ouro nomeia. Com contrato por dispositivo, fica desligado. Se o contrato migrar para citação por artigo, a decisão muda junto.

Os números completos, com as doze configurações medidas, estão no benchmark consolidado. A justificativa de cada valor e os comandos de revalidação estão na estratégia recomendada.

06 Geração

O modelo escolhe IDs. O sistema escreve a citação.

A saída do LLM é um contrato fechado, não texto livre. O verificador aceita, pede uma correção ou devolve uma abstenção segura.

O prompt v2 entrega os dispositivos recuperados em blocos delimitados, com device_id, citação, texto literal, vigência e contexto. O modelo devolve exatamente o JSON do schema. Qualquer campo extra é rejeitado.

Contrato de saída
// o modelo devolve apenas IDs; a citação não é texto do modelo
{
  "resposta": "A medida protetiva pode ser pedida independentemente de boletim...",
  "citacoes": [
    {
      "device_id": "lmp/art19/par5",
      "afirmacao": "A concessão não depende de boletim de ocorrência."
    }
  ],
  "proximos_passos": ["..."],
  "encaminhamentos": ["..."],
  "premissas": ["..."],
  "nivel_confianca": "medio",
  "abstencao": false,
  "motivo_abstencao": null
}

A verificação é determinística. Ela confere o par (device_id, norm_version_id) contra o contexto recuperado, compara os metadados da citação e o texto citado com o literal hidratado do banco, exige citação em toda afirmação e valida as aspas. Não há LLM juiz no caminho padrão.

Aceita

Resposta renderizada com citação canônica e fontes. Exemplo de citação montada pelo sistema: Lei nº 11.340/2006 (Lei Maria da Penha), art. 7º, caput, inciso III.

Recusada

Se a verificação falhar duas vezes, a resposta é substituída por uma abstenção segura com o motivo. O sistema prefere não responder a citar um dispositivo que não sustenta a afirmação.

Na rodada de 150 perguntas, a cobertura de citação ficou em 0,617 e a fidelidade em 0,909. A abstenção acertou 0,923. Esses números medem o pipeline inteiro, não a qualidade jurídica da resposta.

07 Avaliação

O que os números mostram e o que eles não mostram.

150 perguntas; 110 respondíveis; 9 de novembro de 2026.

A rodada de 9 de novembro de 2026 usou 150 perguntas, das quais 110 são respondíveis. As outras 40 são de emergência ou fora do corpus e entram nas métricas de segurança e abstenção. Os valores abaixo vêm do pipeline completo: recuperação, hidratação, geração e verificação determinística.

O recall@10 mede a fração dos dispositivos-ouro recuperados no top-10. O artigo@10 repete a conta no nível do artigo. O groundedness é a fração de afirmações com lastro no contexto recuperado. A abstenção mede o acerto entre abster e responder quando a pergunta está fora do corpus.

O recall@10 do pipeline confere com o do sweep de recuperação: 0,762 nos dois. Isso valida o arranjo experimental no nível do recall. O artigo@10 do pipeline é 0,826; o sweep de recuperação, sem geração, mede 0,835 na mesma configuração. A diferença entre as duas execuções não foi decomposta, então os dois números não devem ser misturados. Em ambos, o artigo certo aparece mais vezes que o dispositivo certo, como esperado num contrato que deduplica por artigo.

citation_precision mede aderência ao gabarito, não alucinação.

O 0,242 conta qualquer citação fora do gabarito de 16 dispositivos como imprecisa. Uma resposta que cita um dispositivo recuperado, pertinente e correto, mas ausente da lista-ouro, perde ponto. Com 16 alvos num corpus de 4.933 dispositivos, o teto prático da métrica é baixo. O número não deve ser citado como taxa de alucinação.

Segurança: 0,750 virou 1,000

A rodada ponta a ponta inicial mediu emergency_routing 0,750. 5 de 20 emergências caíram no caminho normal de resposta, porque o classificador era uma lista de frases literais. Todas as cinco eram variações de superfície que a lista não previa, como "ele está com uma arma e está na minha frente" e "estou escondida no banheiro e ele está batendo na porta".

O classificador foi reescrito em três camadas. Formas iminentes disparam sozinhas. Formas habituais, como "fica me ameaçando", exigem um marcador de presente. Formas passadas disparam, exceto quando a mensagem pergunta sobre prazo, marca o evento como encerrado ("só agora") ou pede caracterização jurídica. O resultado foi 20/20 emergências e 0 falso-positivo em 130 perguntas não-emergência. Os falsos-positivos importam: transformar uma pergunta de prazo em bloco de emergência é resposta errada, ainda que segura. A validação no recorte de 40 perguntas deu emergency_routing 1,000 e abstenção 1,000. Esse 1,000 não é nas 150.

Onde a resposta falha

O critério estrito exige todos os dispositivos-ouro no top-10, todos citados e nenhuma afirmação sem suporte. A tabela mostra quantas perguntas de cada categoria falharam nesse critério.

Falhas por categoria no critério estrito, 150 perguntas
Categoria Falhas Leitura
prazo 11 / 12 Categoria mais frágil.
ação penal 16 / 32 Metade das perguntas não fechou o critério.
medida protetiva 21 / 44 Maior volume de falhas em número absoluto.
serviços 13 / 22 Falha em mais da metade.
emergência 5 / 20 Corrigido depois da rodada.
fora do corpus 0 / 20 A abstenção segurou o recorte.

66 das 150 perguntas falharam. Prazo é a categoria mais frágil, com 11 falhas em 12. Perguntas de prazo dependem de o artigo correto ser recuperado e de a resposta mencionar o prazo certo. Fora do corpus, nenhuma das 20 falhou. Medida protetiva concentra o maior volume absoluto, com 21 falhas em 44 perguntas. O prazo é o próximo alvo da avaliação.

O que estes números não medem

  • As 110 perguntas respondíveis compartilham 16 dispositivos-ouro em 15 artigos. Um recall de 0,76 significa achar o alvo certo dentro de um conjunto de dezesseis, não cobrir violência doméstica.
  • As regras de expansão foram escritas olhando as 20 perguntas semeadas. O conjunto de 110 é in-sample para essas regras, e os números nele são otimistas.
  • Não há avaliação humana. Fluência, utilidade prática, tom e correção jurídica além do lastro da citação não foram medidos.
  • citation_precision mede aderência ao gabarito de 16 dispositivos, não alucinação. Uma citação correta fora do gabarito conta como imprecisa.
  • O p95 foi de 68,2 s contra um orçamento de 8 s. O tempo inclui recuperação, geração e verificação, com chamadas reais ao provedor. A rodada gastou cerca de 50 minutos para 150 perguntas, o que impede uso interativo.

O conjunto é um sinal de regressão, não uma medida de cobertura da lei. Ele mostra se uma mudança piorou o que já funcionava.

O que a rodada sustenta

O pipeline roda de ponta a ponta, a abstenção está sólida e a emergência foi corrigida. O que ela não sustenta: chamar o sistema de pronto ou de SOTA (state of the art).

A definição de cada métrica e o aviso sobre citation_precision estão na metodologia de avaliação. Os números completos, com as doze configurações de recuperação, estão no benchmark consolidado.

08 Limites

O que ainda impede chamar isto de pronto.

O protótipo demonstra o fluxo e mede o que consegue medir. Os itens abaixo são bloqueios reais, não uma lista de melhorias desejáveis.

Seis bloqueios separam o protótipo de um sistema que uma pessoa possa usar sem supervisão. Eles não são melhorias desejáveis. Cada um muda o que o sistema pode afirmar, medir ou prometer, e todos seguem abertos em 9 de novembro de 2026. A lista abaixo é o que impede a palavra "pronto". Ela não é um roteiro de melhorias; é uma lista de condições para o protótipo poder ser usado.

  • Revisão jurídica humana pendente (G4/G6).

    Nenhuma advogada, defensora ou pessoa da rede de atendimento revisou prompt, textos ou respostas. Não há parecer sobre a qualidade jurídica do que o sistema escreve. Os gates G4 e G6 seguem abertos: o G4 combina a avaliação de 20 perguntas com revisão humana, e o G6 combina as 150 com um parecer. A revisão é pré-condição para qualquer uso real, e nenhuma métrica desta página substitui esse parecer. Não há data para essa revisão.

  • Latência p95 de 68,2 s contra 8 s.

    A p50 ficou em 24,5 s. O tempo inclui recuperação, geração e verificação, com chamadas reais ao provedor. A rodada gastou cerca de 50 minutos para 150 perguntas. O uso interativo não está resolvido, e o problema é separado da acurácia: mesmo com recall melhor, a espera continua. A p95 é um limite máximo, e a p50 já mostra a ordem de grandeza. Os 68,2 s vêm de chamadas reais, não de mock, e representam oito vezes o orçamento.

  • Avaliação estreita.

    As 110 perguntas respondíveis compartilham 16 dispositivos-ouro em 15 artigos. As regras de expansão foram escritas olhando as 20 perguntas semeadas, então os números são in-sample. As perguntas são paráfrases de poucos cenários, e o split dev/test não é independente em termos de alvo. O conjunto de 20 perguntas é pequeno: 10 respondíveis, 10 de emergência ou fora do corpus. O resultado compara estratégias entre si. Não é SOTA e não mede cobertura da lei.

  • Caminho alvo 9B/0.6B não operacional.

    Os artefatos locais são GGUF, e o caminho alvo exige safetensors. Ele também precisa de um searcher Qdrant injetado: RETRIEVAL_PATH=target sozinho não monta o pipeline, e o app padrão não monta o caminho alvo. O caminho existe atrás de flag e não teve smoke com os artefatos desta máquina. Sem GPU e checkpoints validados, o fallback é o caminho disponível, e é o que a interface monta por padrão. O alvo não é o caminho que produziu os números desta página.

  • Privacidade e provedor externo.

    O OpenRouter é opt-in. As preferências de retenção zero e não coleta são contratuais, não garantia: precisam ser confirmadas no contrato com o provedor. Sem esse contrato, LLM e embedder precisam rodar localmente. Os logs não têm sink de retenção ainda. LOG_QUESTION_TEXT=false descarta a pergunta por padrão; com opt-in, a redação cobre CPF, telefone, e-mail e CEP. A retenção é uma obrigação para quem criar o sink, não uma propriedade do código atual.

  • Desvios conhecidos.

    O filtro de versão pode abster numa citação explícita de artigo revogado. O esperado seria devolver a versão vigente na data do fato. Payloads versionados do Qdrant não são atualizados quando uma versão fecha. Cerca de 13% das folhas não têm a linha do artigo no mesmo norm_version_id; a expansão degrada para a folha e registra incomplete_context, e o contexto fica menor. Os três desvios estão auditados e registrados; nenhum foi corrigido nesta rodada.

Nenhum desses itens é cosmético. A revisão jurídica e a latência mudam a possibilidade de uso; a avaliação estreita muda o que os números podem afirmar; o caminho alvo e a privacidade mudam onde o sistema pode rodar.

Próximos passos, na ordem

  1. Criar um sink de retenção de logs e validar o X-Request-ID em execução ao vivo.
  2. Rodar um smoke de ingestão real, do download ao índice, com Postgres vivo.
  3. Conseguir checkpoints safetensors e executar o smoke 9B/0.6B (G5).
  4. Rodar as 150 perguntas com build_eval_pipeline contra Postgres e Qdrant.
  5. Submeter prompt, textos e respostas à revisão jurídica humana (G4/G6).

A ordem segue o README: primeiro o que protege dados e prova a operação, depois o que valida o modelo e a resposta.

O protótipo muda de categoria quando a revisão jurídica acontecer, a p95 cair para a casa dos segundos e a avaliação tiver alvos distintos por pergunta. Até lá, os números medem o fluxo, não a utilidade.

Escopo do protótipo

O protótipo serve para demonstrar o fluxo e medir estratégias. Não serve para orientar uma pessoa real sem supervisão jurídica.

09 Rodar

Reproduzir a entrega.

Os comandos abaixo sobem o ambiente local, aplicam as migrações, carregam o corpus e iniciam a API. O README cobre as opções completas.

O ambiente pede Python 3.12 e uv. Docker é opcional e serve para subir Postgres e Qdrant na mesma máquina. O caminho medido usa Postgres como fonte da verdade e Qdrant como índice denso. Postgres guarda normas, versões, dispositivos e o texto literal; o Qdrant guarda os vetores. Sem GPU, o caminho fallback é o que rodou do início ao fim.

Os comandos abaixo são de PowerShell. Em Linux e macOS, troque Copy-Item por cp e a atribuição $env:NOME = "..." por export NOME="...".

1. Dependências

O extra dev instala pytest, ruff e mypy. O extra ml instala sentence-transformers, transformers e torch, necessários para gerar embeddings locais. Só o dev não basta para o índice real.

Dependências
uv sync --extra dev

Para indexar com encoder local, some o extra ml: uv sync --extra dev --extra ml.

2. Configuração

Copie o exemplo e edite o .env. EMBEDDING_MODEL_REVISION precisa de um commit ou tag: um valor vazio ou main faz o encoder real falhar de propósito. O padrão LLM_PROVIDER=mock responde sem chave e sem rede.

Configuração
Copy-Item .env.example .env
Trecho do .env
LLM_PROVIDER=mock
EMBEDDING_MODEL_REVISION=<commit-ou-tag>

A revisão pinada é ignorada quando EMBEDDING_PROVIDER=openrouter; nesse caso o vetor vem do provedor remoto.

3. Infra local

O fallback sobe só o Postgres. O alvo sobe Postgres e Qdrant no perfil target. O Postgres expõe a porta 5432; o Qdrant expõe 6333 e 6334. O .env.example usa 5432 e 6333. Os dados ficam nos volumes pgdata e qdrant_data.

Infra
docker compose up -d db
docker compose --profile target up -d

4. Migrações

scripts/apply_migrations.py não lê o .env. Ele usa DATABASE_URL do processo ou --database-url. Exporte a variável antes de rodar; o script aplica migrations/*.sql em ordem e faz commit por arquivo.

Migrações
$env:DATABASE_URL = "postgresql://app:app@localhost:5432/violencia"
uv run python scripts/apply_migrations.py

A alternativa é passar --database-url direto no comando, sem exportar nada. Dentro de um virtualenv ativado, python scripts/apply_migrations.py também funciona.

5. Ingestão

O comando padrão roda --stage all: baixa, parseia, valida e carrega no Postgres. --offline usa o que já está em data/raw/ e falha se o arquivo não existir. --stage escolhe até onde ir: download, parse, validate ou load.

A seleção aceita --source <id>, --priority P0|P1 ou --all. Os arquivos brutos ficam em data/raw/ com sidecar .meta.json e hash SHA-256. O download é idempotente.

Ingestão
uv run python -m src.ingest.run --priority P0

6. Índice

O índice fallback com encoder local grava vetores densos a partir dos dispositivos já carregados. Exige EMBEDDING_MODEL_REVISION pinado e o extra ml instalado. Sem os dois, o encoder não carrega e o comando falha.

A rodada medida indexou no Qdrant com DENSE_BACKEND=qdrant e qwen/qwen3-embedding-8b via OpenRouter; o .env.example vem com pgvector. O Harrier local não foi usado nessa rodada. Opções da CLI: --source, --database-url e --batch-size.

Índice fallback
uv run python -m src.index.run --path fallback

Para reproduzir o índice medido, use o backend Qdrant e o embedding remoto no .env:

Configuração do índice medido
DENSE_BACKEND=qdrant
EMBEDDING_PROVIDER=openrouter
OPENROUTER_EMBEDDING_MODEL=qwen/qwen3-embedding-8b
OPENROUTER_EMBEDDING_DIMENSIONS=4096
Índice Qdrant
uv run python -m src.index.run --path qdrant-dense `
  --database-url $env:DATABASE_URL --qdrant-url $env:QDRANT_URL

A CLI imprime indexed, skipped e errors, e retorna código 1 se houver erro. Com EMBEDDING_PROVIDER=openrouter, o extra ml não é necessário, mas a chave do provedor é.

7. API e interface

A API serve a interface em /app/; a raiz redireciona para lá. --no-access-log evita que o uvicorn registre a query string. Sem API no ar, a interface abre em modo demonstração explícito, com respostas de exemplo.

API
uv run uvicorn src.api.main:app --no-access-log

A interface fica em http://localhost:8000/app/ e usa o design system ZELIA. O /health responde degraded quando Postgres ou Qdrant estão inacessíveis. Os endpoints são POST /chat, GET /health e GET /sources/{device_id}.

8. Testes

A suíte padrão roda sem Postgres e sem Qdrant. Os testes de integração exigem os dois vivos; o CI sobe os serviços e aplica as migrações antes. O teste do OpenRouter é pulado quando OPENROUTER_API_KEY não está definida.

Testes
uv run pytest -m "not integration"
uv run pytest -m integration
Comandos de qualidade
Qualidade
uv run ruff check .
uv run ruff format --check .
uv run mypy src

Os três comandos são os mesmos que o CI executa nos jobs de lint e de tipos.

O README completo traz as opções de cada comando, o bloco do OpenRouter e a tabela de variáveis. A arquitetura e a stack local descrevem os componentes, o Docker e os contratos de API.

O caminho alvo não está operacional com os artefatos locais.

RETRIEVAL_PATH=target sozinho não monta o searcher Qdrant, o componente que consulta o índice vetorial. Os artefatos locais são GGUF; o caminho exige safetensors, GPU e injeção de um searcher. O caminho fallback é o que rodou na medição.

Para usar o OpenRouter no lugar de modelos locais, siga o bloco Rodando com OpenRouter do README. É opt-in: exige chave e não habilita o caminho alvo, porque o OpenRouter não oferece modelo multivector.

  • Chunking e modelo de dados: árvore legal, identificadores, contexto, versionamento e schema SQL.
